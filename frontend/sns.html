How Amazon SNS works

Publish once; SNS copies the message to every matching subscription

A topic is a logical access point and communication channel. Publishers and subscribers do not need to know about each other. Each subscription chooses a protocol, an endpoint, an optional filter policy, retry behavior, and an optional SQS dead-letter queue.

Use SNS + SQS for production fan-out

Fragile: direct push only

SNS→HTTP worker

A slow worker depends on SNS retries. It has no queue depth for autoscaling, backlog to inspect, or broad recovery window.

Recommended: buffered subscribers

Order service → SNS topic

Billing SQS

Shipping SQS

Analytics SQS

Every consumer owns a queue, retry budget, DLQ, scaling policy, and deployment lifecycle. One outage does not stop the others.

Filter policy rules worth testing
  • • Multiple values in one property are OR.
  • • Different properties are AND.
  • • Operators include exact, prefix, suffix, anything-but, exists, IP, and numeric.
  • • Filter changes can take time to propagate; filters are not authorization.
  • • Missing required properties do not match.
  • • Keep contract tests for every policy.

    


    

      
Reliability

      
Design for unsuccessful delivery and duplicate processing

      

        
Retries
Behavior depends on protocol. HTTP/S policies can tune backoff and throttling. Do not build an endpoint that stays overloaded.

        
Subscription DLQ
An SQS DLQ captures messages SNS could not deliver—not failures after a subscriber successfully accepts one.

        
Idempotency
Record a stable event id before side effects. Standard delivery can be duplicated or arrive out of order.

        
Raw delivery
SQS and HTTP/S can receive the original body without the SNS envelope. Raw SQS delivery supports at most 10 attributes.

      

      
Production observability checklist
□ Alarm on failed notifications
□ Alarm on subscription DLQ depth
□ Track filtered and delivered counts
□ Correlate message id and event id
□ Monitor downstream SQS age
□ Test redrive before incidents

Security and governance

      
Authorize every edge in the fan-out graph

      

        
Publishers
Grant sns:Publish only to required topic ARNs. Use resource policies for cross-account publishers.

        
Subscribers
For SQS, allow sqs:SendMessage from SNS and constrain aws:SourceArn.

        
Encryption
Use TLS and KMS where required. Give SNS and publishers necessary KMS permissions.

        
Private access
An interface VPC endpoint lets private workloads publish without public internet traversal.

        
Sensitive data
Prefer identifiers over secrets or records. One message may be copied to many systems and logs.

        
Webhook verification
Validate SNS signatures and topic ARN, require HTTPS, and handle confirmation deliberately.

      

    


    

      
Cost model

      
Count publishes, payload chunks, endpoint deliveries, and downstream work

      

        
API requests
Standard publish and management requests are metered. Payloads are billed in 64 KB chunks.

        
Delivery protocol
Rates differ for HTTP/S, email, SMS, mobile push, and other endpoints.

        
AWS endpoints
No SNS per-message delivery charge to SQS or Lambda; transfer and downstream services may cost money.

        
Multiplier
One publish to ten subscribers creates ten delivery paths and downstream workloads.

      

      
Worked example: 10 million 4 KB publications with three SQS subscriptions create 10 million SNS publish request units and 30 million SQS sends. Add SQS requests, optional KMS calls, transfer, consumers, logs, and DLQs.

Architecture review

      
Questions every SNS design should answer

      
1. Why pub/sub instead of one work queue?
2. Does each subscriber need an SQS buffer?
3. What stable event id makes processing idempotent?
4. Which fields may filters depend on?
5. Where do delivery and processing failures go?
6. Who owns redrive, alarms, and schema evolution?
7. Are topic, queue, and KMS policies least privilege?
8. What is the cost multiplied by subscribers?

Fully managed

          
What you stop running, and what you still own

        

        
      

      

    

  


  

    
The publisher sends to a topic. The subscriber attaches to that topic. Neither one addresses the other.

    

      
Why

      
    
        
  • The publisher only needs the topic ARN and sns:Publish.
    • 
        
  • A new subscriber is added with Subscribe. The publisher's code does not change.
    • 
        
  • The topic is the contract between them.
    • 
      

    

    
Use it when the sender should not know, name, or wait for whoever is listening.

    
A successful publish means SNS accepted the message. It does not mean the subscriber finished its work.

  


  

    
One topic pushes a copy to every matching subscription. In production, put a separate SQS queue in front of each worker.

    

      
Why

      
    
        
  • Billing, shipping, and audit each get their own copy and their own pace.
    • 
        
  • A slow or failing worker does not block the others.
    • 
        
  • The queue holds the backlog, lets that worker scale on its own, and gives it its own retry window.
    • 
      

    

    
Use it when consumers need a buffer, independent scaling, or retries.

    
SNS does not keep a backlog for consumers to poll. The queue does. Each queue needs a policy that allows the topic, and SQS charges still apply.

  


  

    
The subscriber is software. SNS pushes the event straight to the system that should react.

    

      
Why

      
    
        
  • Lambda runs a short handler without a server to manage.
    • 
        
  • HTTPS reaches a webhook outside AWS.
    • 
        
  • Firehose lands the stream in S3, Redshift, OpenSearch, or a service provider.
    • 
      

    

    
Use it when systems must react to the same event.

    
A Lambda or webhook that is down has a shorter recovery window than a queue. Put SQS in front when the work must wait.

  


  

    
The subscriber is a person. SNS delivers the notification to a phone, an inbox, or an app.

    

      
Why

      
    
        
  • SMS reaches a phone.
    • 
        
  • Email and email-JSON reach an inbox.
    • 
        
  • Mobile push reaches someone using your app.
    • 
      

    

    
Use it when a person must see the notification.

    
This is not application integration. Consent, opt-out, sender identity, sandbox status, destination country, and SMS pricing are part of the design.

The subscription protocol tells SNS how to deliver a copy. These are direct SNS subscription endpoints documented by AWS.

    

      
Amazon SQS
Durable application fan-out. SNS pushes to the queue; workers poll and delete later.

      
AWS Lambda
Invoke short serverless handlers asynchronously.

      
HTTP / HTTPS
Push to webhooks. Confirm the subscription and verify SNS signatures.

      
Amazon Data Firehose
Deliver Standard-topic notifications toward S3, Redshift, OpenSearch, and supported service providers.

      
Email / email-JSON
Human-readable email or a JSON-formatted email endpoint.

      
SMS / mobile push
Text messages and notifications through supported mobile push platforms.

    

    

      
What “many integrations” really means

      
AWS documents a wide variety of event sources and destinations, but it does not currently publish a stable “60+ direct SNS subscription protocols” figure. Direct protocols are the endpoints above. Many additional AWS services publish events to SNS, consume them through Lambda or SQS, or sit behind Firehose. This page avoids an unverified count.

Managed means AWS runs the topic infrastructure. It does not design your event, your subscriptions, or your alarms. SNS pushes a copy to each match. It does not keep a backlog for a consumer to poll later.

    

      

        

          
If you ran the topic

          
        

        
    
          
  • • Install the broker and keep a cluster of nodes across failure domains.
    • 
          
  • • Run a topic exchange and a separate queue binding for every subscriber.
    • 
          
  • • Size disks for the slowest subscriber, then replace a full disk at night.
    • 
          
  • • Replicate data, elect a leader, and rehearse failover.
    • 
          
  • • Patch the operating system and the broker, and plan version upgrades.
    • 
          
  • • Issue certificates and broker user accounts, and retry failed HTTP deliveries yourself.
    • 
        

      

      

        

          
What AWS runs for SNS

          
        

        
    
          
  • • Stores each accepted publish redundantly across Availability Zones before it returns a message ID.
    • 
          
  • • Runs, patches, and scales the service fleet. There is no node to SSH into.
    • 
          
  • • Evaluates each subscription filter and pushes a copy only to the matches.
    • 
          
  • • Retries a failed delivery, then can move it to that subscription's SQS dead-letter queue.
    • 
          
  • • Encrypts the message at rest when you choose an AWS owned key or a KMS key.
    • 
          
  • • Authenticates every API call with IAM and Signature Version 4.
    • 
        

      

    


    

    

    

      

        
What you still own

        
      

      
    
        
  • • Create the topic, each subscription, and the filter policy on that subscription.
    • 
        
  • • Grant sns:Publish to the publisher, and allow the topic to send to each SQS queue.
    • 
        
  • • Put SQS in front of any worker that needs a backlog. SNS does not store one to poll.
    • 
        
  • • Make every subscriber idempotent. SNS can deliver the same message more than once.
    • 
        
  • • Alarm on failed notifications. AWS does not decide that a missed subscriber is an incident.
    •
