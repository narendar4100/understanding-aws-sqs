Project Clearfile · Document Processing Pipeline

Upload the file directly, then route it by what it is

The browser uploads to a private prefix with a presigned URL. EventBridge routes the created object. Queues absorb extract and image work, and SNS tells downstream teams only after a result exists.

The bucket is the front door. The bus is the router.

The uploader role can presign PutObject for incoming/* and nothing else. A .pdf rule targets the extract queue. Image suffixes target the image queue. Any other suffix stays in incoming/. Workers write processed/ and publish DocumentReady. They cannot delete the original while Object Lock governance is active and their role lacks override permission.

Fragile design

The API receives every byte

  • • A 2 GB scan is posted through API Gateway and Lambda.
  • • One function extracts, thumbnails, and emails.
  • • A failed PDF retries in memory until timeout.

Exam-ready design

Direct upload and one queue per job

  • • Lambda sees the object key, not the whole transfer.
  • • Suffix rules separate PDF and image work.
  • • A poison PDF reaches the extract DLQ without stopping images.

What Clearfile will not do for you

  • • It does not scan for malware unless you add that worker.
  • • EventBridge does not move, copy, or delete the object.
  • • A presigned URL written to a log is a bearer token until it expires.
  • • Governance mode is not compliance mode. A privileged principal can override governance. Compliance mode cannot be shortened by anyone until retention ends.
  • • The image queue does not inherit the extract DLQ.

The bytes are an S3 cost, not an EventBridge payload

One million 2 MB PDFs are storage and PUT requests. The events stay small because they contain the bucket and key. A poison file that retries until the DLQ multiplies GET and KMS requests. That is why the DLQ must stop the loop.

Well-Architected checks

  • • Security: Block Public Access, a short presigned URL, separate roles, and encryption.
  • • Reliability: independent queues and DLQs, plus versioning against a bad overwrite.
  • • Performance: the browser uploads directly to S3. Lambda never carries the file.
  • • Cost: lifecycle rules for leftover incoming objects and a DLQ that stops poison-file retries.

Exam drills

A 2 GB scan must enter the system. Which path passes?

Presigned multipart upload to S3. Not an API Gateway or Lambda request body.

notes.txt is uploaded. What runs?

Nothing. No rule matches, and the object remains in incoming/.

One PDF fails forever while photos succeed. What isolates it?

The PDF has its own queue and DLQ. It does not share the image queue.

DocumentReady is published before the result PUT. What is wrong?

The message claims a result that is not durable. Publish after the PUT, and make the indexer tolerate a retry.
