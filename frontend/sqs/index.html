Executive summary

Decouple producers from consumers with a durable queue

Amazon SQS stores messages until a consumer successfully processes and deletes them. Producers can keep accepting work while consumers scale independently, recover from failure, and control throughput. Standard queues optimize for scale; FIFO queues add ordered message groups and send deduplication.

Choose queue semantics

Standard and FIFO solve different workload problems

Standard queue

Maximum throughput, best-effort order

  • • At-least-once delivery; duplicates are possible.
  • • Best-effort ordering across messages.
  • • Scale-out consumers can process many messages in parallel.

Real-life fit

Resize millions of uploaded photos. Every image must be processed, but image B may finish before image A without harming the business.

FIFO queue

Ordered groups with send deduplication

  • • Strict ordering inside each MessageGroupId.
  • • Duplicate send ids suppressed for five minutes.
  • • Different groups can still process concurrently.

Real-life fit

Post debit, reversal, and release events for one bank account in order while other account groups continue independently.

Required for both queue types

      
FIFO deduplication does not replace an idempotent consumer

      

        

          
SQS can redeliver when a worker times out, crashes after committing but before acknowledgement, or returns a failed batch. FIFO suppresses repeated sends with the same deduplication id for five minutes; it does not create a permanent business guarantee.

          
Store the transfer id with a unique constraint in the same database transaction as the ledger change. A retry then becomes a harmless lookup instead of a second debit.

Operational controls

      
Tune delivery behavior deliberately

      

        

          
Visibility timeout

          
Hides a received message while processing. Set it longer than the expected job duration and extend it for variable work. If it expires, another consumer can receive the same message.

        

        

          
Long vs. short polling

          
Long polling waits up to 20 seconds and checks all servers, reducing empty receives and cost. Short polling returns immediately and can produce empty responses.

        

        

          
Delay queue and timers

          
DelaySeconds postpones initial visibility for up to 15 minutes. Standard queues also support per-message timers; FIFO queues use the queue-level delay.

        

        

          
Dead-letter queue

          
Move poison messages after maxReceiveCount is exceeded. Alarm on DLQ depth, retain enough context, fix the cause, then redrive safely.

        

        

          
Retention and payload size

          
Retention ranges from one minute to 14 days. Keep messages compact; larger payloads are metered in 64 KB chunks and very large bodies belong in S3.

        

        

          
Batching and partial failures

          
Send, receive, and delete up to 10 messages per batch. With Lambda, report partial batch failures so successful records are not retried with the failed record.

        

      

      

        
Sent ─▶ delayed/available ─▶ received (in flight) ─┬─▶ success ─▶ deleted
                                                   ├─▶ timeout ─▶ available again
                                                   ├─▶ retention expires
                                                   └─▶ max receives ─▶ DLQ
