Technical deep-dive

Why a ledger cannot stop at SQS Standard

What this burst actually measures

Each button starts exactly 100 fetch() calls inside one synchronous loop, then waits with Promise.all(). The ledger function sleeps 1.5 seconds to stand in for a database transaction: pin the account row, append the journal, flush, commit. Architecture A shares this account's Lambda concurrency quota of 10. Lambda rejects the overflow with HTTP 429 before those calls touch the ledger. The service stays up. The customer transfers that were rejected are simply gone. A reserved cap of 2 can be added after the account quota is raised above 12.

Architecture B removes compute from the admission path. POST /buy-queue is an API Gateway AWS service integration (SQS-SendMessage). The gateway writes $request.body onto the Standard queue training-buffer-queue and returns 200 when SQS has the message. The consumer Lambda, batch size 10, runs the same 1.5 second commit after the browser has finished. The green column fills because the queue absorbed the spike, and the caller no longer shares a fate with the slow commit.

SQS Standard: out-of-order delivery

A Standard queue offers best-effort ordering only. SQS can hand the consumer a later transfer for ACC-9941 before an earlier one: a release before the hold that funded it, or a reversal before the original debit. If the ledger applies each message to a running balance as it arrives, that balance is wrong even though every message is eventually processed. Interest accrual, overdraft decisions, and the end-of-day regulatory snapshot all read that number. The bytes in the queue are intact. The books are not, because posting order is part of the meaning of a ledger.

SQS Standard: duplicate delivery

Standard queues are at-least-once. A message is delivered again when the consumer crashes after commit and before delete, when the visibility timeout expires during the 1.5 second critical section, or when the function retries. The second delivery is another instruction to move 250.00. A consumer that posts every receive will credit or debit the customer twice. That is how an otherwise healthy buffer corrupts a bank: the retry is indistinguishable from a new transfer unless the ledger itself rejects a repeated transaction id.

Why SQS FIFO is the standard for financial ledgers

FIFO is the queue type used for posting pipelines because it supplies the two guarantees Standard withholds, scoped to a message group. Set MessageGroupId to the account id. Transfers for ACC-9941 stay in submission order, while other accounts remain separate groups and still run in parallel, so one hot account does not freeze the bank. Set MessageDeduplicationId to a stable client transfer id (or enable content-based deduplication). For five minutes, a second send of that id is discarded instead of posted again.

FIFO does not replace an idempotency key stored with the ledger. The deduplication window is five minutes, and a consumer can still observe a retry after it has committed. Production posting is FIFO for order, plus a unique transaction id that a database constraint rejects on replay. Exactly-once customer effect is an application property. FIFO is what makes that property operable at queue scale.

The throughput ceiling is the reason teams are tempted to stay on Standard: 300 sends per second without batching, 3,000 with batching, and higher in high-throughput FIFO mode, with a per-group cap so a single account cannot consume the queue. A core ledger takes that ceiling. An unbounded Standard queue that double-posts a transfer costs more than a FIFO queue that makes one account wait a few hundred milliseconds.

Architecture B keeps the Standard queue so the class can see buffering on its own. Architecture C posts the same five transfers, including one repeated Netflix transfer id, to that Standard queue and to the FIFO queue.
