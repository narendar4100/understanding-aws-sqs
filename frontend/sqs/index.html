Amazon Simple Queue Service

A durable queue between the caller and the worker

Amazon SQS is a fully managed message queue. A producer sends a message and gets an acknowledgement as soon as SQS has stored it. The message stays in the queue until a consumer processes it and deletes it, so a slow or unavailable worker does not lose the work.

Executive summary

Decouple producers from consumers with a durable queue

Amazon SQS stores messages until a consumer successfully processes and deletes them. Producers can keep accepting work while consumers scale independently, recover from failure, and control throughput. Standard queues optimize for scale; FIFO queues add ordered message groups and send deduplication.

Choose queue semantics

Standard and FIFO solve different workload problems

Standard queue

Maximum throughput, best-effort order

  • • At-least-once delivery; duplicates are possible.
  • • Best-effort ordering across messages.
  • • Scale-out consumers can process many messages in parallel.

Real-life fit

10,000 product reviews arrive together in a Black Friday sale. One review appearing a couple of seconds early, or twice, does not hurt the business.

FIFO queue

Ordered groups with send deduplication

  • • Strict ordering inside each MessageGroupId.
  • • Duplicate send ids suppressed for five minutes.
  • • Different groups can still process concurrently.

Real-life fit

A customer places an order, then changes their address seconds later. Those two events must stay in that order, or the parcel ships to the old house.

Why we need deduplication

The Network Shield

If a server automatically retries a request during a routine internet hiccup, the duplicate is killed at the gate before it can trigger double warehouse allocations or duplicate shipping labels.

Teams rarely choose a self-run broker for a new cloud app. They keep one because something outside the queue forces it.

Protocol lock-in

A certified payment system on JMS

A bank's core system, built years ago, posts payments through IBM MQ using JMS and XA two-phase commit with its database. Rewriting it for SQS means re-certifying a payment platform. SQS has no XA transactions.

No internet

A factory floor with its own network

Robots and sensors publish MQTT on a plant network with no route to AWS. Messages must flow even when the internet link is down. A local broker, such as RabbitMQ or Mosquitto, runs inside the plant.

Data residency

A hospital or defense network

Policy says patient or classified data never leaves the building. Every queue must run on hardware the organization owns and audits.

Broker features

Routing inside the broker

RabbitMQ exchanges route by topic or header, and support priority queues and request-reply. SQS has none of these. On AWS you would add SNS or EventBridge, or split priorities into separate queues.

What your team now owns

A cluster of at least three nodes for high availability, disk sizing, OS and broker patching, version upgrades, certificates, user accounts, monitoring, backups, and failover drills. A full disk or a split cluster at 3 AM is your incident.

Middle path: if you need the protocol but not the servers, Amazon MQ runs ActiveMQ or RabbitMQ for you. AWS patches it. You still choose the broker size and a maintenance window.

If nothing forces a broker, SQS is usually the default on AWS: no servers, no capacity plan, and you pay only per request.

Traffic spikes

A flash sale at midnight

Orders jump from 50 a minute to 50,000. A standard queue absorbs the spike with no resize, while the order workers drain it at a safe rate. A self-run broker would need disk and nodes sized for that peak in advance.

Small team

No one on call for a broker

A five-person product team ships features, not broker patches. SQS has no nodes to fail over, and IAM controls who can send and receive.

Quiet workloads

Nightly or seasonal jobs

A tax-filing app is busy for two months a year. An idle queue costs almost nothing. An idle broker cluster costs the same every hour.

Serverless

Lambda as the consumer

Lambda polls SQS for you, scales consumers with the backlog, and moves failures to a dead-letter queue. No consumer servers to run either.

What changes when you move from a broker

  • • Consumers poll. SQS does not push to them.
  • • The visibility timeout and DeleteMessage replace a broker acknowledgement.
  • • No exchanges or priorities. Use SNS or EventBridge to route, and separate queues for priority.
  • • Messages are capped at 1 MiB and kept at most 14 days.
  • • Clients use the AWS SDK. A JMS 1.1 library exists for Java, but it covers only part of JMS.

How to set it

At least 6 × the Lambda function timeout

If you use a batch window, add MaximumBatchingWindowInSeconds as well. The function timeout itself must be less than or equal to the visibility timeout, or Lambda rejects the event source mapping.

The message stays hidden while a consumer works. Lambda may retry a throttled invocation several times. If the message becomes visible during those retries, a second worker processes it too.

Example

function timeout 30s → visibility timeout ≥ 180s

With a 10-second batch window, use at least 190 seconds. The default of 30 seconds is too short for almost any Lambda consumer. Do not set it for hours either: a real failure then waits that long before it can be retried.

How to set it

Use long polling. Set WaitTimeSeconds from 1 to 20.

Short polling is WaitTimeSeconds = 0. It returns immediately and may look at only a subset of SQS servers, so it can come back empty even when a message exists.

An empty receive is still a billable request. Long polling waits for a message and checks all servers, so you make fewer calls and miss fewer messages.

i Where those servers are

Serverless means you do not run or patch a host. SQS still runs on AWS-owned machines in the Region. AWS does not publish the racks or the host count. It does publish this behavior: each message is stored redundantly on multiple servers. A short poll asks a weighted random subset of them. A long poll asks all of them and waits.

The call waits up to 20 seconds. If a transfer arrives at second 3, it returns then. If nothing arrives, it returns empty once, instead of hundreds of immediate empty polls.

How to set it

0 to 15 minutes. Not longer.

A standard queue can delay one message with DelaySeconds, or every message with a queue delay. A FIFO queue uses only the queue delay. Do not sleep inside Lambda to wait: you pay for the wait, and the visibility timeout must cover it.

Use a delay when the work is valid now but should not run yet. The message is stored immediately and becomes visible later.

Example

DelaySeconds = 600

A signup is accepted now, and the welcome email is sent 10 minutes later. The consumer never sees the message during those 10 minutes, so it does not need to hold a connection open.

How to set it

Set maxReceiveCount, then alarm on the DLQ

The source queue and the dead-letter queue must be the same type: standard with standard, or FIFO with FIFO. After maxReceiveCount receives, SQS moves the message aside instead of retrying it forever.

A poison message is one that fails every time, often because the body is bad. Left on the source queue, it is retried until retention ends and can block a FIFO message group.

Example

maxReceiveCount = 5

A transfer with a missing account id fails five times, then lands in the DLQ. You alarm on the DLQ depth, fix the handler, and redrive the message. The other transfers keep moving.

How to set it

1 minute to 14 days. Default is 4 days.

A message body can be 1 byte to 1 MiB. Above 1 MiB, store the body in S3 (up to 2 GB) and put a pointer on the queue. Lowering retention can delete messages already in the queue.

Retention is how long an unprocessed message survives. Payload size is also a cost control: SQS meters each 64 KB chunk as a request.

Example

200 KB body → 4 request chunks

Keep the queue message to the transfer id and amount. Put a statement PDF in S3. Use 4 days when a consumer outage is measured in hours. Use 14 days only if the backlog can really sit that long and still be valid.

How to set it

Up to 10 messages, and report the failures

Turn on ReportBatchItemFailures on the Lambda event source mapping. Return only the failed message ids in batchItemFailures. Lambda then deletes the ones that succeeded.

One API call can send, receive, or delete up to 10 messages, which cuts request cost. Without a partial-batch response, one bad message makes Lambda retry the whole batch.

Example

10 messages, number 7 fails

With a partial response, Lambda deletes the other 9 and retries only number 7. Without it, all 10 become visible again. The consumer still has to be idempotent, because a successful message can be delivered once more if the delete does not finish.

Deduplication and idempotency

Two safety layers protect two different failure points

Deduplication protects the send side: the queue refuses a second copy. Idempotency protects the business side: if the same message is processed twice, the account is still debited once. You need both.

01FIFO only. A send with the same MessageDeduplicationId within 5 minutes is accepted and not delivered again, even if the first copy was already deleted.

02Two ways to set the id. Pass it on every send, or turn on content-based deduplication, which hashes the body but not the attributes.

03Standard has no deduplication. Delivery is at least once, so a duplicate can reach the consumer.

04Redelivery happens on both queues. A timeout, a failed batch, or a crash before DeleteMessage makes the message visible again.

05Key on the business id. Use the transfer id, not the SQS MessageId. A producer retry gets a new MessageId for the same transfer.

06Claim and apply together. Insert the id behind a unique key in the same transaction as the debit. Delete from SQS only after that commit.

Optional implementation example: PostgreSQL transactional inbox

ON CONFLICT DO NOTHING is official PostgreSQL syntax—not an AWS, SQS, or generic SQL command. It means “if this unique transfer id already exists, do not insert another row.” MySQL commonly uses INSERT IGNORE; DynamoDB commonly uses a conditional PutItem. 

BEGIN;

INSERT INTO processed_messages (transfer_id)
VALUES ('txn-netflix-002')
ON CONFLICT DO NOTHING;

-- Continue only if the insert created one row.
UPDATE account_balance SET balance = balance - 250.00 ...;
INSERT INTO ledger_journal (...) VALUES (...);

COMMIT;

Important: the id claim and the business update must commit together. A separate “check then update” has a race condition when two workers run concurrently.

If the side effect is outside your database, such as a payment or shipping API, pass the same idempotency key to that API. One database transaction cannot cover an external call and the SQS delete together.

Operational controls

Tune delivery behavior deliberately

Visibility timeout

Hides a received message while processing. Set it longer than the expected job duration and extend it for variable work. If it expires, another consumer can receive the same message.

Long vs. short polling

Long polling waits up to 20 seconds and checks all servers, reducing empty receives and cost. Short polling returns immediately and can produce empty responses.

Delay queue and timers

DelaySeconds postpones initial visibility for up to 15 minutes. Standard queues also support per-message timers; FIFO queues use the queue-level delay.

Dead-letter queue

Move poison messages after maxReceiveCount is exceeded. Alarm on DLQ depth, retain enough context, fix the cause, then redrive safely.

Retention and payload size

Retention ranges from one minute to 14 days. Keep messages compact; larger payloads are metered in 64 KB chunks and very large bodies belong in S3.

Batching and partial failures

Send, receive, and delete up to 10 messages per batch. With Lambda, report partial batch failures so successful records are not retried with the failed record.

One message, from acceptance to an ending

The cards above set the timers and the retry limit. This is the path those settings control. A message is stored, hidden while a worker has it, and then it ends in one of three places.

Timeout sends it back

The worker still has it when the visibility timeout ends. It returns to Waiting, and another worker can take it.

Retention drops it

Nobody finishes it before the retention period. SQS deletes it. There is no copy left to replay.

Too many receives

It fails until maxReceiveCount. SQS moves it to the dead-letter queue for a person to inspect.

Failure isolation

A dead-letter queue stops one bad message from failing forever

A DLQ is a separate SQS queue for messages the consumer could not process after repeated receives. It preserves the failed payload for investigation while healthy messages keep moving. SQS does not create, repair, or monitor the DLQ for you.

Two different moves. RedrivePolicy sends the exhausted message into the DLQ. After the fix, a DLQ redrive sends it back to the source queue for a normal receive.

The operational loop

  1. 1Alarm when ApproximateNumberOfMessagesVisible on the DLQ is greater than zero.
  2. 2Inspect the body, attributes, receive count, logs, and trace or correlation id.
  3. 3Fix the data or deploy a consumer that can process it safely.
  4. 4Redrive to the source queue at a controlled rate, then verify the business commit.

Configuration rules

  • • Create the DLQ first. The source queue points to its ARN through a RedrivePolicy.
  • • Types must match: Standard → Standard, FIFO → FIFO.
  • • Choose maxReceiveCount from 1–1,000. Allow enough attempts for temporary failures, but do not retry a poison message for days.
  • • Set DLQ retention longer than source retention so operators have time to investigate.
  • • Restrict allowed source queues with a RedriveAllowPolicy.

Not an automatic repair

The message waits. A team or runbook must diagnose, correct, and redrive it.

Not a permanent archive

DLQ retention is still at most 14 days. Copy evidence elsewhere if audit rules require longer storage.

Not always right for strict FIFO

Moving one failed event aside can break an end-to-end sequence. Stop the group instead when later events must never pass it.

Under the service

A queue is a broker. SQS hides the broker from you.

On premises, a team runs the broker process on its own machines. In AWS, SQS is that broker, operated by AWS. You call an HTTPS API. You do not install, patch, or cluster it.

Classic broker you operate

RabbitMQ, ActiveMQ, IBM MQ

  1. 1. The producer connects to the broker.
  2. 2. The broker writes the message to a durable queue and acknowledges.
  3. 3. A consumer pulls it, or the broker pushes it.
  4. 4. The consumer acknowledges. The broker then deletes it or advances the offset.

Amazon SQS

Same job, no broker in your account

  1. 1. The producer calls SendMessage over HTTPS.
  2. 2. SQS stores redundant copies on its own servers and returns 200.
  3. 3. The consumer calls ReceiveMessage. The message is hidden.
  4. 4. After success, the consumer calls DeleteMessage.
